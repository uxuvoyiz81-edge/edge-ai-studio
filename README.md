# EDGE // AI STUDIO — 多 AI 协作平台

> 推翻旧观念，零成本打造热门赚钱的 AI 开发工作站。
>
> 一个人 + 三个 AI，就是一支完整的开发团队。

---

## 一、项目定位：暗黑极客风多 AI 开发工作站

EDGE // AI STUDIO 不是又一个 AI 聊天壳子，也不是简单的模型调用器。

它的定位是：**暗黑极客风的多 AI 开发工作站** —— 一个把“想法 → 需求 → 代码 → 产品 → 上线赚钱”全链路装进一个浏览器页面的工作台。

### 它要解决什么问题？

1. **一个人能力有限，多 AI 各有所长**：有的擅长架构，有的擅长写代码，有的擅长独立思考、挑毛病。
2. **AI 工具分散、切换成本高**：聊天、编程、画图、做游戏、查资料来回跳转，灵感都被切碎了。
3. **做产品门槛被高估了**：很多人以为做产品要服务器、要团队、要很多钱。其实浏览器 + 免费额度 + 静态部署，就能先跑起来。
4. **只聊天不赚钱**：AI 对话的终点不应该是聊天记录，而是能上线的产品、能留存的用户、能验证的收入。

### 它面向谁？

- 独立开发者、副业探索者、想用 AI 做产品赚钱的创作者
- 喜欢极客风、暗黑 UI、键盘流、高信息密度界面的用户
- 相信“小步快跑、先上线、再迭代”的实干派

### 一句话理解 EDGE

> **EDGE = 边缘 + 锋利 + 先人一步。**
> 在别人还在讨论 AI 能不能赚钱的时候，你已经用多 AI 协作把产品做出来、上线了。

## 二、核心功能

### 1. 多模型聚合：一个入口，多个大脑

- 同时接入多个主流大模型，在同一个界面里提问、对比、追问。
- 同一个问题，看不同模型的回答风格、解法和细节，避免被单一模型的偏见带偏。
- 支持按任务选模型：架构用一个，写代码用一个，润色文案用一个，审查用一个。
- 对话历史统一管理，方便回溯、收藏、导出和复用提示词。

**设计目标：** 不站队任何一个模型，让模型之间互相竞争、互相补位。

### 2. AI 竞技场：让 AI 互相 PK，答案越辩越明

AI 竞技场是 EDGE 最有辨识度的功能。

- 输入同一个需求，多个 AI 同时给出方案。
- 可以设定评判维度：正确性、可实现性、成本、用户体验、赚钱潜力。
- 让 AI 互相评审、互相找茬：A 指出 B 方案的漏洞，B 反驳并优化自己的方案。
- 最终由用户拍板，选出最值得落地的那一个版本。

**为什么需要竞技场？**

因为 AI 的第一次回答往往不是最好的。经过对比、辩论和修正，答案质量会明显上升。竞技场把“多 AI 协作”从口号变成可操作的流程。

### 3. AI 工具箱：开箱即用的赚钱小工具集合

工具箱的原则是：**小、快、准、能直接用**。

- **提示词工具**：需求拆解、提示词优化、角色设定、批量生成。
- **开发工具**：代码解释、代码重构、正则生成、SQL 生成、报错排查、接口文档生成。
- **内容工具**：标题生成、短视频脚本、种草文案、产品介绍、SEO 描述。
- **效率工具**：会议纪要、周报生成、翻译润色、表格整理、灵感收集。

每个工具都聚焦一个具体场景，输入少、输出直接可用，优先做那些“用户愿意收藏、愿意分享、愿意反复回来用”的工具。

### 4. 游戏中心：边玩边验证，用游戏留住用户

游戏中心不是附属品，而是 EDGE 的流量和留存引擎。

- 提供轻量、即开即玩的浏览器小游戏：反应类、解谜类、策略类、AI 生成关卡类。
- 支持 AI 生成玩法：让 AI 出题、出关卡、做 NPC 对话，把“AI 能力”变成“可玩的体验”。
- 游戏即内容：好玩的游戏天然适合截图、录屏、分享，能带来自然传播。
- 游戏即验证：一个小游戏从想法到上线只要几天，是验证多 AI 协作流程的最佳练手项目。

**逻辑闭环：** 工具带来实用价值，游戏带来停留和分享，竞技场带来深度讨论，三者互相导流。

## 三、技术方案：零成本、浏览器端优先、Cloudflare Pages 部署

### 核心原则

1. **零成本启动**：不买服务器、不预付云资源，先用免费额度和静态托管跑通最小闭环。
2. **浏览器端优先**：能放在前端做的，就不依赖后端；能用本地存储的，就不先建数据库。
3. **先上线，再完善**：第一版追求“能用、能看、能分享”，而不是“完美”。
4. **可替换、可迁移**：模型接口、部署平台、存储方案都做成可替换的，不被任何一家锁定。

### 技术选型

| 环节 | 方案 | 说明 |
| --- | --- | --- |
| 前端 | HTML + CSS + JavaScript / 前端框架 | 暗黑极客风 UI，响应式，移动端可用 |
| 样式 | 暗黑配色 + 霓虹点缀 + 等宽字体 | 突出终端感、极客感、速度感 |
| 模型调用 | 各模型官方 API / 兼容接口 | 按需接入，支持切换和对比 |
| 数据存储 | 浏览器本地存储（LocalStorage / IndexedDB） | 第一版零后端，保护隐私，上手零门槛 |
| 部署 | Cloudflare Pages | 免费、快速、全球加速，推送即部署 |
| 版本管理 | GitHub | 代码、文档、协作流程都在这里 |

### 架构示意

```text
用户浏览器
  ├── 多模型聚合界面
  ├── AI 竞技场界面
  ├── AI 工具箱界面
  └── 游戏中心界面
        │
        ▼
  模型 API（按需调用）
        │
        ▼
  Cloudflare Pages（静态托管 + 全球分发）
```

### 为什么选 Cloudflare Pages？

- 零成本起步，适合独立开发者验证想法。
- 与 GitHub 协作顺畅，提交代码即可自动部署。
- 访问速度快，全球节点分发，用户体验好。
- 后续需要后端能力时，可以平滑扩展，而不用推倒重来。

### 成本与风险控制

- 严格控制 API 调用量：先做缓存、复用和提示词优化，避免无意义的重复调用。
- 关键功能提供“演示模式 / 本地示例”，没配 API Key 也能体验界面和流程。
- 不在前端暴露敏感密钥；需要服务端中转的能力，后续再单独接入。
- 定期复盘：哪些功能有人用、哪些没人用，用数据决定下一步做什么。

## 四、三 AI 协作分工：一个人就是一支团队

EDGE 的开发方式本身就是它要展示的方法论：**让三个 AI 各司其职，互相配合。**

| 角色 | 担任者 | 核心职责 | 产出物 |
| --- | --- | --- | --- |
| 架构师 | ChatGPT | 定方向、定结构、定标准 | 产品定位、技术方案、页面结构、提示词框架 |
| 执行手 | Muse | 高速落地、写代码、改细节 | 可运行的页面、功能实现、样式优化、Bug 修复 |
| 独立搭档 | Hy4 | 独立思考、挑毛病、补盲点 | 评审意见、替代方案、风险提醒、创意补充 |

### 协作流程

1. **架构师先行**：ChatGPT 给出整体定位、功能清单、技术方案和页面结构。
2. **执行手落地**：Muse 按照架构方案，快速写出第一版可运行的代码。
3. **独立搭档评审**：Hy4 独立审查，不看“怎么写出来的”，只看“好不好用、有没有漏洞、有没有更好的做法”。
4. **三方合流**：把评审意见合并进下一版，架构、实现、评审形成闭环。
5. **用户拍板**：所有 AI 的建议，最终由人来决定做与不做、做多少、做到什么程度。

### 分工的好处

- **避免单点思维**：一个 AI 容易自我肯定，三个 AI 更容易发现问题。
- **速度与质量兼得**：架构保证方向不错，执行保证速度够快，评审保证质量不掉。
- **可复制**：这套分工不只适用于 EDGE，也适用于任何一个人想用 AI 做产品的人。

> **核心理念：人不必什么都会，但要会指挥、会判断、会拍板。**
> AI 负责出力，人负责定方向和做决策。

## 五、14 天验证计划：从想法到可验证的产品

目标不是 14 天做出一个完美产品，而是 **14 天验证“这条路走得通”**。

### 第一阶段：第 1–3 天，打地基

- [ ] 第 1 天：确认定位、名称、口号、目标用户，搭好仓库和部署流程
- [ ] 第 2 天：完成首页骨架：暗黑极客风视觉、导航、四个核心模块入口
- [ ] 第 3 天：完成多模型聚合最小版：能输入、能对比、能保存历史

**阶段验收：** 别人打开链接，能一眼看懂 EDGE 是做什么的，能动手试一次核心功能。

### 第二阶段：第 4–7 天，做核心

- [ ] 第 4 天：AI 竞技场最小版：同一问题多模型对比 + 简单评分
- [ ] 第 5 天：AI 工具箱第一批工具：至少上线 5 个高频小工具
- [ ] 第 6 天：游戏中心第一款小游戏：即开即玩，能分享
- [ ] 第 7 天：整体联调：统一视觉、修复明显 Bug、补齐移动端体验

**阶段验收：** 四个核心功能都有可用的最小版本，流程能跑通，没有致命 Bug。

### 第三阶段：第 8–11 天，做传播

- [ ] 第 8 天：写好 README、产品介绍、截图和演示动图
- [ ] 第 9 天：做 3 个“能直接分享”的内容：工具演示、竞技场对比、游戏试玩
- [ ] 第 10 天：发布到 1–2 个合适的渠道，收集第一波真实反馈
- [ ] 第 11 天：根据反馈做一轮优化：只改最影响体验的 3 个问题

**阶段验收：** 至少有真实用户访问、试用并给出反馈；知道用户最喜欢和最吐槽的是什么。

### 第四阶段：第 12–14 天，做验证

- [ ] 第 12 天：统计数据：访问量、停留时长、工具使用次数、游戏游玩次数
- [ ] 第 13 天：验证变现可能：哪些功能值得做付费版、会员、打赏或广告？先做一个最小验证
- [ ] 第 14 天：复盘 + 决策：继续做、换方向、还是砍掉？写下下一阶段计划

**最终验收标准（满足任意两条即算验证通过）：**

1. 有用户主动收藏、分享或二次访问；
2. 有用户愿意为某个功能付费、打赏或留下联系方式；
3. 有明确的数据证明某一个功能是“留得住人”的。

### 验证期间的纪律

- 每天只做当天清单，不贪多、不返工、不追求完美。
- 功能做减法：能砍的先砍，能用现成方案的绝不重造。
- 以用户反馈为准：用户说没用的功能，再酷也要先放下。
- 赚钱是验证，不是口号：14 天结束时，必须能回答“它怎么赚钱”。
